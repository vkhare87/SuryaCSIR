## 2. AI-native readiness

### What is already solid

- **Grounded Q&A loop works end to end** (`rag/`): router → whitelisted structured
  function *or* PageIndex document traversal → cited answer. `rag/router.py` falls back to
  the document route on any parse failure, and a structured route may only name a function
  in the catalog. No free-form SQL from the model. This is the right safety shape for agents.
- **Calls run as the user.** `rag/api.py` builds a per-request client from the user's
  bearer token, so RLS scopes what the model can read. An agent built on this inherits it.
- **Two worker loops already exist** (`rag/worker.py`, `ingest/worker.py`): claim → process
  → mark, per-item isolation, stale-claim requeue. This is a usable host pattern for
  background agents — no new runtime needed.
- **Derived "what needs doing" logic exists** (`src/lib/dashboard/myActions.ts`,
  `src/lib/digest/*`) and is unit-tested.

### Gaps that block "agents running in the background"

| # | Gap | Why it matters | Where |
|---|---|---|---|
| G1 | **Action logic runs only in the browser.** `deriveMyActions` and the digests run when a page renders. Nothing evaluates them when nobody is logged in. | A background agent has nothing to read. Deadlines are found only if someone visits. | `src/components/MyActions.tsx`, `src/lib/dashboard/myActions.ts` |
| G2 | **No general notifications table.** Only `pms_notifications`. | Agents need one place to write findings that the bell, My Actions, and email all read. | WP-2 A1 |
| G3 | **No scheduler.** Workers poll a queue; nothing runs on a clock (daily digest, 90-day expiry sweep). | Every "manage activities" agent is time-driven. | WP-2 E4 |
| G4 | **No tool layer for actions.** The model can *read* (catalog functions, documents). It cannot *propose* an action. | An agent that only reads is a report generator. | new |
| G5 | **No agent audit/approval record.** | Non-goal says "no autonomous decisions". So every agent output must be a *suggestion* a human accepts, and that acceptance must be logged. | new |
| G6 | **Service key in workers.** RAG worker uses `SUPABASE_SERVICE_KEY` (bypasses RLS). | Fine for indexing. Not fine for an agent that writes per-user notifications — scope must be enforced in the RPC. | `rag/config.py:34`, `deploy/` |
| G7 | **Production host not stood up; CPU-only LLM is 3–4 min/question.** | Background agents multiply model calls. Without a GPU host they will not keep up. | CLAUDE.md tech debt |

### Recommended shape (fits the non-goals)

1. **Move rules server-side first** (A1). Port `myActions.ts` rules to SQL views or one
   Python module the worker imports. Write rows to a new `notifications` table
   (`user_id, kind, severity, entity_ref, body, source='rule'|'agent', status`). RLS: owner
   reads own rows only.
2. **Add a clock to the existing worker** — a `--sweep` mode run by cron / Task Scheduler.
   No new service. Deterministic rules first; they need no LLM.
3. **Then add LLM agents as "suggesters"**, each a small function in the worker:
   - Report-due nudger (PMS / progress reports / proposals) — drafts the reminder text.
   - Data-health agent — reads `dataHealth.ts` output, opens a helpdesk ticket draft for the
     data owner.
   - Scheduled brief (E4) — runs a saved `/query` and posts the answer with citations.
   Each writes `source='agent'` notifications with a proposed action. A human clicks
   *Accept* → existing RPC runs as that human. The agent never calls a state-changing RPC.
4. **Log every accept/dismiss** to the existing audit trail. This gives the evaluation data
   (precision of suggestions) and keeps the "no autonomous decisions" rule true.

## 3. Role separation (UI)

### What exists

- One `ACCESS_MAP` drives nav and route guards (`src/constants/access.ts`). Good.
- 14 role dashboards under `src/pages/dashboards/`. Role switcher in the top bar.
- Feature kill switches per route (`/admin/features`).

### Problems

| # | Problem | Evidence |
|---|---|---|
| R1 | **Nav is feature-shaped, not role-shaped.** Sections are "Unified Human Resource / Research Ops / Governance" for everyone. A Director sees ~18 items; a SystemAdmin sees ~25. A Scientist sees Intelligence, Explore Graph, R&D Monitor, Partnerships — analytics pages they rarely need — next to their two real jobs (PMS report, progress report). | `src/components/layout/Sidebar.tsx:31` |
| R2 | **Same analytics pages for very different roles.** `/intelligence`, `/explore` open to Scientist and Director alike. The page does not change what it leads with. | `ACCESS_MAP` |
| R3 | **Role switch is silent.** Dropdown shows raw role keys (`DivisionHead`, `EmpoweredCommittee`), no "acting as" confirmation. Avatar letter is the role initial, not the person. | `src/components/layout/Layout.tsx:84` |
| R4 | **Every role loads every table.** `DataContext` fetches ~31 tables at login for all roles; client scoping only for DivisionHead/Technician. RLS read-scoping (`20260718000001`) is applied (verified 2026-10-20), so the database trims rows per user — the cost left is speed: one big load for every role, needed or not. | `src/contexts/DataContext.tsx:226`, `:79` |
| R5 | **Header copy is desktop/exec-only.** "CSIR-AMPRI Executive Terminal" for every role. | `Layout.tsx:62` |

### Recommendation

Give each role **one home with three blocks**: *My tasks* (inbox, WP-5 C), *My numbers*
(2–4 KPIs for that role), *Ask SURYA* box. Then a short nav:

| Role group | Primary nav (≤6) | Everything else |
|---|---|---|
| Scientist / ProjectStaff / Student | Home, My PMS report, My projects, Progress reports, Ask, Calendar | "More" menu |
| HOD / DivisionHead | Home, My division, Approvals, PMS evaluations, Ask, Calendar | "Analytics" section |
| Director / EmpoweredCommittee | Home (exec brief), Approvals, Analytics, Ask | "Operations" section |
| HR / Finance / System / Master admin | Home, Data, Users & access, Monitoring | admin tools |

Implementation is small: add a `primaryFor: Role[]` field to `NAV_SECTIONS` items, render
primary items first and collapse the rest under "More". `ACCESS_MAP` stays the only
permission source.

## 4. Mobile vs desktop

### What exists

- `UIContext` gives `isMobile / isTablet / deviceType`. Sidebar becomes a drawer;
  `DataTable` switches to card mode on mobile/tablet.
- Roadmap non-goal: no native app; mobile is read-only.

### Problems

| # | Problem | Evidence |
|---|---|---|
| M1 | **Only 7 files adapt to device.** Everything else is the desktop page squeezed. | grep `isMobile|deviceType` |
| M2 | **No bottom nav / quick actions on phone.** Every move needs hamburger → long list. | `Sidebar.tsx` |
| M3 | **Fixed widths.** 38 `min-w-[NNNpx]` / `w-[NNNpx]`; 13 non-responsive `grid-cols-3+`. | grep |
| M4 | **"Mobile is read-only" is not enforced.** PMS wizard, proposal form, Data Management upload all render on phones. | `src/pages/pms/ReportEdit.tsx`, `src/pages/DataManagement.tsx` |
| M5 | **Hover-only affordances** (3× `opacity-0 group-hover`) are invisible on touch. | grep |
| M6 | **Full data load on mobile networks** (same as R4). | `DataContext.tsx` |
| M7 | **Design-token debt: ~1,470 raw colour classes** (`bg-[#141413]`, `text-rose-700`…), tracked in `eslint.design-debt.json`. Sidebar and top bar are among them. Makes dark mode and density inconsistent. | grep |

### Recommendation

- **Phone = "check and approve" app.** Bottom bar with 4 items: Home (inbox), Ask, Calendar,
  Me. Show the inbox, KPI cards, detail pages, and approve/acknowledge buttons. Hide
  uploads, wizards, graph explorer, admin pages behind a "Open on desktop" card. Put the
  rule in `ACCESS_MAP` as a second field (`desktopOnly: true`) so it is one source again.
- **Desktop = full workbench.** Keep current sidebar, with the role-first ordering above.
- Fix M3/M5 per page as touched; burn down M7 starting with `Layout.tsx` + `Sidebar.tsx`
  (every page shows them).

## 5. Suggested order

1. Load per role, not everything at login (R4/M6). RLS scoping is already live.
2. WP-2 A1 notifications table + server-side rules sweep (G1–G3).
3. Role-first home + short nav (R1–R3, WP-5 C/E/R).
4. Mobile bottom bar + `desktopOnly` flag (M1–M4).
5. LLM suggester agents on top of A1 (G4–G5), once a GPU host exists (G7).
